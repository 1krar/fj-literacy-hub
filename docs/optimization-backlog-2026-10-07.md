# 比赛检索工作台：优化清单与下一版验收

更新：2026-10-07。依据：本轮用户要求、历史需求、当前源码只读核对，以及 model-workflow-lab/reports/实验报告.md。

本文件保留需求整理时的源码快照；下方“当前缺口”描述的是优化前状态。2026-10-07 用户授权开始实施，并说明千问和书生目前免费额度充足，因此优先优化速度、准确性和稳定性，费用统计保留但不作为当前主要调度依据。

## 本轮实施状态

第二批已实施：紧凑工作台、统一设置弹窗、Shift＋点击重试/Alt＋Shift＋Enter 快捷重做、OCR/建议/答案独立复核与版本切换。复核不覆盖原结果、不自动切换；采用新原题后标记旧建议和答案。输入版本绑定允许在其他复核仍运行时采用原题，迟到回复保持旧版本标记。不同环节的失败分别保留重试目标，复核失败优先读取完整响应。Cloudreve 和多端同步按用户要求暂不实施。

验证：67 项 Python 和 33 项 JS 通过，Edge 360px/480px 主页面与真实 PiP、设置收纳、Shift 点击和快捷键、复核版本切换通过。真实千问合成算术题三阶段复核耗时分别约 1.89/2.45/1.39 秒，小窗弹窗可操作，无 JS 错误；此例不代表复杂题准确率或典型速度。部署版本 993b9d0a。

- 已实现全局 API 六并发、单供应商六并发、双 API 优先分配给较空闲的供应商、网页独立串行通道、排队数显示与任务隔离。
- 默认千问一次请求返回原题和建议，先发布完整原题；可按 OCR/建议/答案分别选择供应商及书生具体模型。跨模型 OCR 后续仅发送识别文本。
- API/网页共用任务界面；独立答案选择包含在小窗中，千问作答思考可选，书生保持平台默认。后台保留返回模型、请求耗时与用量，不虚构费用或进度百分比。
- 新增书生本机加密配置；每题提交时冻结 API 配置，排队期间改配置不串题。重试优先复用完整回复；新答案上下文独立于建议上下文。
- 通过离线并发/任务隔离/流式原题/跨模型/缓存重试测试和 360px/480px 主页面及实际 PiP 浏览器验收。六并发真实调用的限流、速度与识题/答案准确率仍需实测；本轮没有因此宣称模型准确率相等。
- 后续：题目编辑及结果版本、限流冷却与取消、准确率标注实验、多端云端后台、持久题目历史、可选本地 OCR。先以真实比赛题评测，再决定增加额外模型或复核调用。

## 1. 已确认要求与默认策略

本轮最终验证：62 项 Python（含实际 Edge PiP 验收）和 33 项 JS 检查通过。一次 HTTP 拒绝测试出现 Windows 10053，整套重跑通过；此连接关闭边缘情况仍值得后续持续观察。真实千问合成六题（1 截图、5 文本）并发峰值为 6，全数返回原题/建议/正确算术答案，整批约 2.75 秒，单请求约 1.56–2.45 秒。仅用于验证通道，不代表复杂比赛题准确率或典型耗时。测试题已归档，升级前四道完成题目已恢复。书生主助手尚未配置 Key，未进行真实书生调用。静态界面部署版本为 6feff2bd。

- 用户指定 API 默认并发使用 6。下一版定义为全局同时执行最多 6 个 API 请求；只选千问时允许千问独立使用全部 6 个位置。排队题数与请求并发数分别统计。
- 网页模型继续采用独立串行通道；同一模型的网页会话不直接套用 API 六并发。
- 保留统一任务工作台，区分网页调用与 API 调用，接入百炼/千问网关及书生平台，允许扩展其他平台。
- OCR、检索建议、答案可独立选择模型；问答案支持本题临时改选。默认每个环节只执行一个模型，复核是额外明确操作。
- 全页和小窗粘贴/拖图、自动建题、窄任务标签、后台执行、先有结果先展示继续保留。
- 模型分配还处于比较阶段。依据当前实验，建议暂用 Qwen3.8 Flash 关闭思考完成原题与检索建议；DeepSeek 可选回答/复核。不是两模型准确率已被证明等价。
- 自动画答案开关保留默认关闭；开启后允许随建议附带初步答案。不得自动增加每题双模型调用。

## 3. 当前缺口

- scripts/ctrl_dispatch.py 的每个模型线程池仍 max_workers=1，以 busy 集合限制每模型一次一个任务，千问也被串行化。
- scripts/ctrl_multi.py 仍先单独 OCR，再继续生成建议；没有迁入实验 A 的合并流程。
- 问答案沿用 assigned 模型，不能独立选择答案模型；三环节跨模型配置尚未完成。
- scripts/qwen_api.py 当前固定 qwen3.8-flash，尚未提供书生和通用模型注册。
- API 虽为流式网络请求，但当前主要累计完整正文后返回，原题分段提前展示仍需实现。
- API 历史保留图片和此前消息，后续请求可能重复输入；同一上下文并发写入还需防冲突。
- 正式助手没有完整记录 usage、费用、每环节请求时间与配置快照。
- 服务重启后任务和原图不能恢复；主页面与小窗刷新/选题更新需在六并发下重新验证。

## 4. P0：先完成速度、隔离与恢复

### P0-1 真正的 API 六并发

- 用正在执行请求计数管理容量，不用布尔 busy；API 与网页调度分开。
- 全局 API 上限默认 6，可设置平台子上限；不可把书生不同 Key 当成独立额度。
- 手动问答案、用户触发重试优先于尚未发送的后台任务；不打断已发送请求，并避免长期饿死新题。
- 用户在查看、复制或等待的题目不占 API 位置。
- 明确显示运行中 x/6、排队 n；排队时间计入用户总等待，同时与请求本身时间分开。
- 429 识别为限流，按响应提示退避，显示真实状态；身份/权限错误不反复重发。
- 六并发是目标，不是当前实验已经证明的千问独立承载能力。限流时短暂降低发送速度，界面说明原因。

### P0-2 迁入 Qwen 合并识题流程

- 清晰文字截图：一次回复原题在前、关键词和网站建议在后；明确关闭思考。
- 使用有明确边界的分段格式或流式事件，只有原题段完整后才确认可用，不能把半句当作识别完成。
- 原题完成即展示；建议随后更新，允许按需启动答案请求。
- 文字输入跳过 OCR；独立 OCR 模型设置启用时使用真正的分步流程。
- 公式/图表保留原图，不能因 OCR 有文本就丢弃视觉信息。
- 原题已正确但建议失败时保留原题，仅恢复/重跑建议；部分答案不得冒充完整结果。

### P0-3 多题结果不串题

- 请求绑定 task_id、stage_id、request_id、原题版本与配置快照。
- 修改原题后旧结果不覆盖新版本；同一环节重复点击防重。
- API 每题独立上下文；建议和答案并行时使用各自消息快照，禁止同时覆盖共享 history。
- 改全局模型只影响后续提交；已有题临时改选通过本题操作明确指定。
- 取消排队任务立即移出队列；已发送任务的取消不承诺平台停止计费，迟到结果不能重新激活题目。

### P0-4 分情况重试

- 刷新：重新取本机状态，不发模型请求。
- 网页回复已出但读取失败：先恢复并读取绑定的原对话。
- 网页对话消失：使用保留原题/原图重新执行必要环节，不读别的对话。
- API 格式解析失败：先用保存的完整回复修复解析，避免马上重新付费调用。
- 网络中断/超时：明确说明完成状态未知；重发可能重复计费，保留手动重试入口。
- 报告包含题目与环节 ID、平台、模型、有效参数、时间、状态码和脱敏错误，不包含 Key 或完整推理内容。

## 5. P1：模型选择、界面与检索准确性

### P1-1 平台和环节设置

- 顶部选择网页/API；详细配置折叠，平时只显示当前策略。
- 平台配置有官方预设地址、模型列表、图片能力、思考控制和就绪状态；不混用自营/百炼/书生模型 ID。
- 页面启动自动检查配置与连接状态，失败时显示原因、设置/重连入口；API 已配置不冒充调用已验证。
- OCR、建议、答案分别设置，支持跟随与固定选择；不支持图片的模型不能作为 OCR 候选。
- 问答案按钮旁下拉选择模型，小窗也有；复核保留首次结果并标来源。
- 简单任务关闭思考；复杂任务可开启。自动按题型分配先使用可解释规则，不每题额外问一次路由模型。

### P1-2 紧凑小窗和稳定操作

- 顶部仅一行窄任务标签，题号/短标题加文字状态；颜色只作辅助。
- 每题记住滚动位置、原题展开与结果选择；更新不能改变焦点或把正在点击的按钮移走。
- 输入栏保持一行，图片预览折叠；复杂配置留在主页面，小窗保留临时答案模型选择。
- 原题强调否定词、时间、地区、单位、限制条件；突出显示不得改动原文，可编辑后重新分析。
- 保留分项复制，关键词/检索式可点击复制；大范围复制按钮不重新加入。
- 状态按实际阶段显示，不制作未知耗时的虚假百分比；保留耗时和失败入口。

### P1-3 网站推荐与答案依据

- AI 提取主题、字段、时间/地区及资料类型；已收录网址优先由数据库规范化匹配。
- 保留主站、高级检索、相似和上级入口；默认适量显示，更多折叠。相关度不足时不硬塞网站凑数。
- 未收录站点允许补充，未经核验网址标待核验；链接检查异步/缓存，不能阻塞原题与建议展示。
- 登录限制、验证码、HEAD 不支持等不能直接判死链；已有用户确认网址保留。
- 统计数、数据库结果、标准状态等标记待来源核验；模型自报置信度不显示为准确率。
- 自动附带答案和独立问答案分别记录。已有答案时提供追问/复核入口，避免误以为第一次答题必须再发一次请求。
- 导航缩写继续保留，补显式别名与常用排序；测试 zw 同时能找到知网和高级知网。

## 6. P2：数据保留、多端与进一步优化

- 可选本机任务历史，支持恢复、归档、清空；截图的存储大小和保留期单独管理。
- 同时有主页面和小窗时保持同一任务状态；网页模型标签只清理助手创建且不再需要的标签，保留浏览器进程/登录。
- 记录原题出现、建议出现、首次可用答案、人工修正、排队、重试与 Token usage；费用未知不填 0。
- 手机自动 API 使用需要远程后端；Cloudflare Pages 继续提供界面，服务端保存凭证、限流与任务状态。列入后续阶段，不在本轮部署。
- 本地 OCR、更多模型、自动路由与超时后备用模型属于后续候选，先通过实测证明收益。
- 自动备用/竞速会增加费用，两模型相同答案也可能共享 OCR 错误，不能默认作为正确性证明。

## 7. 补测与验收

- 当前实验只验证过混合批次全局峰值 6，千问峰值 3；后续单独测试千问六并发及答案环节。
- 同批截图、相同有效配置、轮换顺序；人工评分关键文字、检索建议、答案，各项分开。
- 标明平台与实际返回模型，关闭思考能力未核实不能写成已关闭；顺序/并发及不同配置不混合统计。
- 测试 API 六请求真正重叠、第七个排队、手动问答案优先、重试防重复、重启/刷新、改题后迟到回复、小窗切题及网页对话切换。
- 质量测试覆盖否定词、年份、单位、公式、表格、多选题、多个相似机构与数据库查询题。
- 有代表性的少量试题作筛选，扩大样本后再评价慢请求和准确率；保留一部分题目验证分配规则，避免只对样例优化。
- 真实调用由用户明确启动；本轮只做清单整理，没有执行付费补测。

## 8. 研究依据与应用边界

- LiteLLM 路由文档：https://docs.litellm.ai/docs/routing 。参考并发控制、限流、超时和重试机制，项目不必立即引入完整代理栈。
- RouteLLM 官方仓库：https://github.com/lm-sys/RouteLLM 。参考模型选择和按实际任务校准，不能照搬不同模型组合的收益。
- FrugalGPT，TMLR 2024：https://lingjiaochen.com/papers/2024_FrugalGPT_TMLR.pdf 。参考选择性升级，注意额外调用产生的成本和等待。
- Interruption in visual search: a systematic review，Frontiers in Psychology 2024：https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2024.1384441/full 。支持关注中断与任务恢复，据此建议前台稳定、后台并行；不是对本产品提速幅度的直接证明。
- UI/UX Pro Max 的 loading feedback 指南：保持布局、焦点和可访问的忙碌状态，等待有反馈，不使用一律相同的动画/时间阈值。

## 9. 推荐实施顺序

1. API 六并发＋题目/版本隔离＋失败恢复。
2. Qwen 合并识题与建议＋完整分段提前显示。
3. 网页/API 两种方式＋书生接入＋独立答案模型＋环节设置。
4. 小窗紧凑化、网站与答案核验提示、真实耗时及使用量。
5. 本机历史、多端后台、更多模型及经验证的自动分配。

实施过程中应同步更新 README、说明页和启动页文案，防止界面承诺与实际功能不一致；上线另按项目部署说明执行。
